VERDIKT

Datový model nových engine je solidní a fail-closed logika u fyziky, časové osy
a validace anotací skutečně funguje. Blokující nálezy nejsou v návrhu, ale
ve třech místech: (1) release gate je jeden bajt od červeného buildu,

(3) tisková cesta nečeká na vykreslení vizuálů.

Žádný z nálezů P0/P1 níže se nevyskytuje v dokumentech AUDIT-1.3.30,

P0-1  PERFORMANCE BUDGET JE 1 BAJT OD ČERVENÉHO BUILDU — DEMONSTROVÁNO
--------------------------------------------------------------------------------
Kde:      scripts/build.mjs (chybí minifikace), config/performance-budget-*.json
Stav:     largestInlineScriptBytes = 379 999 / 380 000 B

Reprodukce:
  V src/js/36-all-subject-safety.js jsem do jediné promptové věty přidal
  slovo "čísla, " (rozdíl 9 bajtů):
      'PŘEDMĚTOVÁ PŘESNOST: nevymýšlej fakta, citace ani hodnoty.'
    → 'PŘEDMĚTOVÁ PŘESNOST: nevymýšlej fakta, čísla, citace ani hodnoty.'
  Výsledek:
      npm run build            → OK
      node scripts/qa-p3-quality.mjs → FAILED
      budget.largestInlineScriptBytes: 380 008 <= 380 000   ✗
      summary: 30/31, failed 1

Dopad:
  Jakákoli redakční úprava české promptové vrstvy — jedno doplněné slovo,
  jedna upřesněná instrukce pro model — shodí CI. To je stav, ve kterém
  se přestane vyvíjet obsah a začne se šetřit znaky. Už teď to vedlo
  k rozhodnutím, která nemají s výkonem nic společného (mazání PWA ikon
  kvůli bajtům, ruční minifikace zdrojů — viz P2-10).

Kořenová příčina:
  Build JS vůbec neminifikuje. scripts/build.mjs čte src/js/*.js a spojuje
  je verbatim ('\n;\n'). CSS se ořezává o komentáře a whitespace, JS ne.
  Autor to kompenzuje ruční minifikací zdroje — tedy platí maintainability
  za něco, co má dělat nástroj.

Měření (esbuild --minify --target=es2020 na už ručně minifikovaný bundle):
      380 000 B  →  336 305 B     úspora 43 694 B (11,5 %)
  To je bez jediné změny zdrojového kódu. Rezerva by skočila z 1 B na ~44 kB.

Druhá vrstva problému — budget měří špatnou veličinu:
      inline bundle:  raw 379 999 B   gzip 114 444 B
      index.html:     raw 489 961 B   gzip 141 242 B
  GitHub Pages servíruje gzip/brotli. Reálný přenos je ~141 kB, což je
  v naprostém pořádku. Zmrazený limit tedy reguluje nekomprimované bajty,
  které nikdo nikdy nestáhne, a přitom už blokuje obsahovou práci.

Návrh opravy:
  1. Přidat esbuild (nebo terser) do scripts/build.mjs na spojený inline
     bundle. Zdroje nechat čitelné.
  2. Přepočítat budget proti gzipované velikosti, ne raw. Raw ponechat
     jako druhý, výrazně volnější limit proti nekontrolovanému růstu.
  3. Teprve potom rozminifikovat zdroje zpět do čitelné podoby (P2-10).
  4. Doporučený nový limit: gzip entry ≤ 170 kB, raw entry ≤ 600 kB.


P0-2  EDU_TRACE TIŠE ZAHAZUJE CELOČÍSELNÉ DĚLENÍ (FAIL-OPEN)
--------------------------------------------------------------------------------
Kde:      src/modules/algorithm-trace-engine.js, funkce cleanLines()
Kód:      .replace(/\/\/.*$/,'')

Reprodukce (Node):
  traceProgram({program:['a = 7','b = a // 2','PRINT b']})
  → vars: {a:7, b:7}   output: ["7"]   errors: []   steps: 3

  Očekáváno: b = 3, nebo tvrdá chyba "nepodporovaný operátor".
  Skutečnost: řádek se ořízne na "b = a", program doběhne, vygeneruje se
  kompletní trace tabulka, která je celá špatně, a nikdo se nic nedozví.

Proč to je vážné:
  Python je v gymnaziální informatice dominantní jazyk a "//" je jeho
  standardní celočíselné dělení. Model, který dostane instrukci
  "školní pseudokód", bude "//" produkovat běžně. Engine je přitom
  v release notes prodáván jako fail-closed: "mimo definovaný školní
  pseudojazyk se vstup odmítne". Tady se neodmítne — tiše se přepíše.

Druhý dopad stejného řádku:
  traceProgram({program:['s = "http://skola.cz"','PRINT s']})
  → errors: ["Řádek 1: Neuzavřený řetězec."]
  Komentář se strhává před tokenizací, takže "//" uvnitř řetězce rozbije
  literál.

Návrh opravy:
  Strip komentářů provádět až po tokenizaci, nebo alespoň:
  - "//" uvnitř řetězcového literálu ignorovat,
  - "//" v pozici binárního operátoru (mezi dvěma operandy) NEbrat jako
    komentář a buď implementovat jako Math.floor(a/b), nebo vyhodit
    explicitní chybu "celočíselné dělení není podporováno".
  Doporučuji implementovat — je to pět řádků a odstraní to celou třídu chyb.


P0-3  EDU_REACTION NEOVĚŘUJE SYMBOLY PRVKŮ (FAIL-OPEN)
--------------------------------------------------------------------------------
Kde:      src/modules/reaction-engine.js, funkce parseGroup()
Kód:      if(/[A-Z]/.test(c)){const m=s.slice(i).match(/^[A-Z][a-z]?/) ... }

Parser přijme jako prvek libovolnou sekvenci [A-Z][a-z]? bez porovnání
s tabulkou prvků. Bilance pak proběhne nad fiktivními prvky.

Reprodukce (Node):
  balanceReaction('NAOH + HCl -> NACl + H2O')
  → coefficients: [1,1,1,1]   errors: []
    (parser rozložil NAOH na N, A, O, H — "A" není prvek)

  balanceReaction('Q2 + R2 -> 2 QR')   → [1,1,2]   errors: []
  balanceReaction('Xx + O2 -> XxO2')   → [1,1,1]   errors: []

Dopad:
  Nejběžnější chemický překlep — zápis všemi velkými písmeny (NAOH, NACL,
  CACO3) — projde jako korektně vyčíslená rovnice a dostane se do klíče
  i do bilanční tabulky pod nadpisem "Prvek | Levá | Pravá", kde bude
  sloupec s neexistujícím prvkem A.

Poznámka k WEIGHTS:
  Tabulka molárních hmotností má 45 prvků. Chybí mj. Cs, W, U, Y, Zr, Mo,
  Sb, Te. Pro gramové převody to failuje korektně
  ("Pro převod gramů chybí podporovaná molární hmotnost"), ale bilance
  proběhne, protože ta hmotnosti nepotřebuje. Po zavedení whitelistu
  se z toho stane jednotné chování.

Návrh opravy:
  Zavést zmrazený seznam platných symbolů prvků (postačí H–Og, 118 položek,
  ~700 B) a v parseGroup odmítnout vše mimo něj s hláškou
  "Neznámý symbol prvku: XX". WEIGHTS pak může zůstat řidší tabulkou
  hmotností — validita symbolu a znalost hmotnosti jsou dvě různé věci.


P0-4  EDU_REACTION VRACÍ U NEJEDNOZNAČNÝCH ROVNIC LIBOVOLNÉ ŘEŠENÍ
--------------------------------------------------------------------------------
Kde:      src/modules/reaction-engine.js, funkce positiveVector()

Když má bilanční soustava jádro dimenze ≥ 2, rovnice má nekonečně mnoho
platných vyčíslení. Kód v takovém případě hrubou silou prochází kombinace
(6^n, strop 5000) a vrátí PRVNÍ nalezený kladný celočíselný vektor —
bez jakéhokoli varování.

Reprodukce (Node):
  balanceReaction('C + O2 -> CO + CO2')
  → coefficients: [4,3,2,2]   errors: []
  (opakovaně stejný výsledek — je to deterministické, ale chemicky arbitrární;
   stejně platné je 2,3,... a nekonečně mnoho dalších poměrů)

Dopad:
  Do klíče se dostane jedna z nekonečně mnoha možností prezentovaná jako
  "ta správná". Žák, který vyčíslí jinak a správně, bude podle klíče
  označen za chybného. To je horší než chyba renderingu — je to chyba,
  která se dostane do hodnocení.

Rozpor s deklarací:
  AUDIT-1.3.30 uvádí "Bilance používá přesnou racionální lineární algebru,
  nikoli numerické hádání." To je pravda pro nalezení jádra. Ale výběr
  jednoho vektoru z vícerozměrného jádra hádání je.

Návrh opravy:
  V positiveVector(): pokud basis.length > 1, vrátit chybu
  "Rovnice není jednoznačně vyčíslitelná; doplň chybějící látku nebo zadej
  očekávané koeficienty." Volitelně: pokud uživatel dodal
  expectedCoefficients a ty leží v jádru, přijmout je jako doplňující
  podmínku a ověřit je — to je pedagogicky správné chování.

  zjistí až v hodině.

  2. Umožnit režim "ukázat prvních N kroků + posledních M" místo tvrdého
     odmítnutí — u pracovního listu to je pedagogicky lepší než chyba.
  3. Odlišit hlášku "překročen limit kroků" od "podezření na nekonečnou smyčku"
     (druhá jen tehdy, když se stav proměnných mezi iteracemi nemění).

     které se nevejdou.

P2-11  DROBNÉ SÉMANTICKÉ NESROVNALOSTI EDU_TRACE
--------------------------------------------------------------------------------
  a) Modulo záporných čísel:  -1 % 3  →  -1  (JS zbytek)
     V Pythonu i v matematické konvenci  →  2.
     U pseudokódu inspirovaného Pythonem to dá špatný výsledek bez varování.

  b) Desetinná aritmetika bez zaokrouhlení:
     x = 0.1 + 0.2  →  v trace tabulce se vytiskne 0.30000000000000004
     Do pracovního listu pro žáka to nepatří. renderTrace by měl hodnoty
     formátovat (např. Number(v.toPrecision(12))).

  c) Porovnání polí je vždy false:
     A = [1,2] / B = [1,2] / r = A == B  →  false
     primary() vrací clone(v), takže === porovnává reference.

  d) Nepodporované, ale běžné konstrukce školního pseudokódu:
       IF x > 0 THEN PRINT x        →  "Nepodporovaný příkaz"
       ELSE IF x > 1 THEN           →  "Nepodporovaný příkaz"
     Promptová instrukce přitom hlásí podporu "IF/ELSE" bez uvedení, že
     ELSE IF je nutné psát jako vnořené IF uvnitř ELSE a že jednořádkový
     zápis neexistuje. Model bude obojí generovat.

  Návrh: (a) a (b) opravit v engine/rendereru, (c) zdokumentovat,
  (d) doplnit do promptové instrukce nebo implementovat ELSE IF
  (je to jeden regex a jedno rozvinutí na vnořené IF).

"adversariálních vstupů": překlepy, nepodporovaná syntaxe, nejednoznačná
zadání, degenerované případy. Je to levnější než korpus a chytá jinou
třídu chyb. Korpus pak měří to, k čemu je určený — sémantickou věrnost
na reálných materiálech.
